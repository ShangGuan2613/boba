Boba · Lesson 02

工具失败，也要回一张小票

模型可以点错单、点到不存在的菜、遇到机器故障。Harness 不能让一个异常把店关了。

约 14 分钟 · 前置 Lesson 01 · 工具协议速查 · Harness 地图

1. 三张没人接的单

第 1 课的闭环跑通了。现在开始接真顾客，问题立刻出现：

场景 Harness 里发生什么 顾客看到什么
“来一杯珍珠奶茶。” order_create(item=...) 缺尺寸、冰量、糖度 → TypeError 冒到顶层 没有回复，对话结束
“有会员折扣吗？” 模型调用未注册的 get_discount → KeyError 没有回复，对话结束
店员想查库存 inventory_check 抛 RuntimeError 没有回复，对话结束

三次崩溃，同一个原因：一个 tool_use 发出去了，却没有 tool_result 回来。循环不是被模型结束的，是被 Harness 抛出的异常炸掉的。

2. 一条硬规则

1 个 tool_use → 1 个 tool_result

每一个工具调用，必须恰好收到一个结果。成功是结果，失败也是结果。这不是提示词里的建议，是循环必须守住的不变量。

未知工具、缺参数、工具抛异常、护栏否决、预算耗尽——全都算。Harness 的职责不是替模型把事情做成，而是把发生的事如实回填，让模型决定下一步：问顾客、换工具，还是停。

要做到这一点，tool_result 至少满足三个条件：

  • 对得上：tool_use_id 和请求完全一致。
  • 标得清：失败时 is_error: true，不要伪装成成功。
  • 能行动：错误里有 code、message 和下一步 hint。

Anthropic 的工具设计指南也强调：错误信息要具体、可操作，让模型知道怎么改，而不是只丢一句“出错了”。Writing effective tools for agents

3. 四种回填，同一个形状

点下面的标签，看同一条 tool_use 在四种情况下各自收到什么。注意：失败也没有让循环停。

顾客说“来一杯”，但没说规格

调用
{"tool_use_id": "call_1", "name": "order_create",
 "args": {"item": "boba_milk_tea"}}

回填
{"tool_use_id": "call_1", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "missing_argument",
   "message": "order_create 缺少参数：size, ice, sugar",
   "hint": "先问顾客缺的那一项，不要自己猜。"}}}

模型下一步：问“中杯还是大杯？冰量、糖度呢？”拿到回答后，再发一次完整调用。不是猜一个默认值硬做。

模型编了一个不存在的工具

调用
{"tool_use_id": "call_2", "name": "get_discount",
 "args": {"order_id": "B1001"}}

回填
{"tool_use_id": "call_2", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "unknown_tool",
   "message": "没有注册工具：get_discount",
   "hint": "只调用已注册的工具；不要重复调用不存在的工具。"}}}

模型下一步：不要原样重试。改用已注册的工具，或者直接告诉顾客“目前没有这个功能”。

工具自己坏了

调用
{"tool_use_id": "call_3", "name": "inventory_check",
 "args": {"item": "boba_milk_tea"}}

回填
{"tool_use_id": "call_3", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "tool_failed",
   "message": "inventory_check 执行失败：RuntimeError: 冰箱传感器离线",
   "hint": "告诉顾客稍等；需要时换一个只读工具确认状态。"}}}

模型下一步：说“稍等，我确认一下”，可以换一个只读工具；不能假装库存正常。

参数齐了，正常出杯

调用
{"tool_use_id": "call_4", "name": "order_create",
 "args": {"item": "boba_milk_tea", "size": "中杯",
          "ice": "少冰", "sugar": "三分糖"}}

回填
{"tool_use_id": "call_4", "is_error": false,
 "content": {"ok": true, "data": {
   "order_id": "B1001", "item": "珍珠奶茶",
   "size": "中杯", "ice": "少冰", "sugar": "三分糖",
   "total": 12}}}

模型下一步：回复“中杯少冰三分糖，12 元”，结束这一轮。成功和失败走的是同一条回填路径。

上面是 Harness 内部的对象；发给真实 Messages API 时，content 会被序列化成字符串或内容块，但 tool_use_id 与 is_error 的语义不变。

4. 代码：把异常关进边界

关键不是“多写几个 if”，而是让所有工具执行都经过同一个入口。未知工具在 registry 里处理：

class ToolRegistry:
    def run(self, call):
        tool = self._tools.get(call.name)
        if tool is None:
            return self._error(call, "unknown_tool", ...)

        content = tool.run(call.args)
        return ToolResult(call.id, content, is_error=not content["ok"])

参数校验和异常捕获在工具边界内处理：

class Tool:
    def run(self, args):
        missing = [k for k in self.required if k not in args]
        if missing:
            return error_content("missing_argument", ...)

        try:
            return {"ok": True, "data": self.fn(**args)}
        except Exception as exc:
            return error_content("tool_failed", ...)

这里的 except Exception 不是“吞异常”。它只守在工具边界，把失败转换成模型能读的结果；在完整 Harness 里，同一处还会写 trace。它不捕获 BaseException，所以 Ctrl-C 仍然能停。

完整可运行代码：boba/tool_protocol.py。五个测试覆盖缺参数、未知工具、工具异常、成功和“每个调用恰好一个结果”。在仓库根目录跑：

python3 -m unittest discover -s tests -v

5. 错误码是给模型的下一步

同一个 is_error: true，不同 code 对应不同恢复动作。不要把所有失败都写成“未知错误”。

code 触发 模型应当
missing_argument 必填参数没给 问顾客缺的那一项
unknown_argument 给了工具没声明的参数 删掉或改正参数后重发
unknown_tool 调用了未注册的工具 改用已注册工具，或告知做不到
tool_failed 工具内部抛异常 告知稍等，必要时换只读工具
permission_denied 后续 护栏否决 解释规则，不要绕过
budget_exhausted 后续 轮数 / 调用数 / 时间耗尽 停止并交接，不要继续试

6. 奶茶店 ↔ 协议

店里发生什么 协议里是什么 正确处理
顾客点单没说冰量 missing_argument 店员问“冰的还是热的？”
顾客点了菜单上没有的配方 unknown_tool “菜单上没有这个”，不硬做
封口机卡住 tool_failed “稍等，我看一下”，不假装成功
小票和杯子对不上 tool_use_id 不匹配 出杯给错人；必须在回填时配对
一出错就直接关店 异常逃出循环 顾客被晾着；必须转成结果

8. 这一课故意没做的事

  • 没有做完整的 JSON Schema 类型 / 枚举校验，只查了必填和未知参数。
  • 没有重试和退避——tool_failed 先交回模型，不自动重试。
  • 没有错误分类统计，也没有 trace 落盘。
  • 没有权限护栏——permission_denied 只占了个位置。
