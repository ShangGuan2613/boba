Boba · Lesson 02

工具失败，也要回一张小票

模型可以点错单、点到不存在的菜、遇到机器故障。Harness 不能让一个异常把店关了。

约 14 分钟 · 前置 Lesson 01 · 工具协议速查 · Harness 地图

1. 三张没人接的单

第 1 课的闭环跑通了。现在开始接真顾客，问题立刻出现：

场景 Harness 里发生什么 顾客看到什么
“来一杯珍珠奶茶。” order_create(item=...) 缺尺寸、冰量、糖度 → TypeError 冒到顶层 没有回复，对话结束
“有会员折扣吗？” 模型调用未注册的 get_discount → KeyError 没有回复，对话结束
店员想查库存 inventory_check 抛 RuntimeError 没有回复，对话结束

三次崩溃，同一个原因：一个 tool_use 发出去了，却没有 tool_result 回来。循环不是被模型结束的，是被 Harness 抛出的异常炸掉的。

2. 一条硬规则

1 个 tool_use → 1 个 tool_result

每一个工具调用，必须恰好收到一个结果。成功是结果，失败也是结果。这不是提示词里的建议，是循环必须守住的不变量。

未知工具、缺参数、工具抛异常、护栏否决、预算耗尽——全都算。Harness 的职责不是替模型把事情做成，而是把发生的事如实回填，让模型决定下一步：问顾客、换工具，还是停。

要做到这一点，tool_result 至少满足三个条件：

  • 对得上：tool_use_id 和请求完全一致。
  • 标得清：失败时 is_error: true，不要伪装成成功。
  • 能行动：错误里有 code、message 和下一步 hint。

Anthropic 的工具设计指南也强调：错误信息要具体、可操作，让模型知道怎么改，而不是只丢一句“出错了”。Writing effective tools for agents

3. 四种回填，同一个形状

点下面的标签，看同一条 tool_use 在四种情况下各自收到什么。注意：失败也没有让循环停。

顾客说“来一杯”，但没说规格

调用
{"tool_use_id": "call_1", "name": "order_create",
 "args": {"item": "boba_milk_tea"}}

回填
{"tool_use_id": "call_1", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "missing_argument",
   "message": "order_create 缺少参数：size, ice, sugar",
   "hint": "先问顾客缺的那一项，不要自己猜。"}}}

模型下一步：问“中杯还是大杯？冰量、糖度呢？”拿到回答后，再发一次完整调用。不是猜一个默认值硬做。

模型编了一个不存在的工具

调用
{"tool_use_id": "call_2", "name": "get_discount",
 "args": {"order_id": "B1001"}}

回填
{"tool_use_id": "call_2", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "unknown_tool",
   "message": "没有注册工具：get_discount",
   "hint": "只调用已注册的工具；不要重复调用不存在的工具。"}}}

模型下一步：不要原样重试。改用已注册的工具，或者直接告诉顾客“目前没有这个功能”。

工具自己坏了

调用
{"tool_use_id": "call_3", "name": "inventory_check",
 "args": {"item": "boba_milk_tea"}}

回填
{"tool_use_id": "call_3", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "tool_failed",
   "message": "inventory_check 执行失败：RuntimeError: 冰箱传感器离线",
   "hint": "告诉顾客稍等；需要时换一个只读工具确认状态。"}}}

模型下一步：说“稍等，我确认一下”，可以换一个只读工具；不能假装库存正常。

参数齐了，正常出杯

调用
{"tool_use_id": "call_4", "name": "order_create",
 "args": {"item": "boba_milk_tea", "size": "中杯",
          "ice": "少冰", "sugar": "三分糖"}}

回填
{"tool_use_id": "call_4", "is_error": false,
 "content": {"ok": true, "data": {
   "order_id": "B1001", "item": "珍珠奶茶",
   "size": "中杯", "ice": "少冰", "sugar": "三分糖",
   "total": 12}}}

模型下一步：回复“中杯少冰三分糖，12 元”，结束这一轮。成功和失败走的是同一条回填路径。

上面是 Harness 内部的对象；发给真实 Messages API 时，content 会被序列化成字符串或内容块，但 tool_use_id 与 is_error 的语义不变。

4. 后厨窗口：一张单子的旅程

把 Harness 想成店里的后厨窗口。前台店员（模型）把顾客的需求写成一张点单，递进窗口；窗口后面的师傅（工具）负责做。前台只负责判断和说话，不亲自进后厨；真正动手的是窗口后面的师傅。窗口不能把单子吞掉，也不能把烧焦的锅直接扔到前台。

它只做一件事：接单，回小票。

前台写一张点单
→
后厨窗口查菜单、查单子
→
师傅照配方做
→
小票回到前台
店里的话 代码里的话
一张点单：单号、菜名、规格 ToolCall(id, name, args)
回执小票：同一个单号、做没做成、原因 ToolResult(tool_use_id, content, is_error)
后厨窗口：所有单子的唯一入口 ToolRegistry
窗口师傅：照着配方做 Tool.run
配方卡：要什么料、哪些必须写 Tool 的 required / properties
退单原因：哪一步没过、怎么办 error_content(code, message, hint)

窗口接过一张单子，只查三件事：

  1. 菜单上有这道菜吗？没有 → 退单，写 unknown_tool。
  2. 单子写全了吗？缺冰量、糖度 → 退单，写 missing_argument。
  3. 师傅做的时候机器坏了吗？坏了 → 退单，写 tool_failed。

三道里任何一道没过，窗口都要回一张小票。不是关窗，不是沉默，不是把异常扔到前台。

class ToolRegistry:                  # 后厨窗口
    def run(self, call):             # 接一张单
        tool = self._tools.get(call.name)
        if tool is None:             # 菜单上没有这道菜
            return self._error(call, "unknown_tool", ...)

        content = tool.run(call.args)  # 师傅照配方做
        return ToolResult(call.id, content, is_error=not content["ok"])  # 回小票
class Tool:                          # 一张配方卡
    def run(self, args):             # 师傅动手
        missing = [k for k in self.required if k not in args]
        if missing:                  # 单子没写冰量
            return error_content("missing_argument", ...)

        try:
            return {"ok": True, "data": self.fn(**args)}
        except Exception as exc:     # 封口机卡住
            return error_content("tool_failed", ...)

为什么异常不能扔出窗口？如果师傅把烧焦的锅直接扔到前台，前台只会被烫到，顾客什么也听不到。这里的 except 不是把故障藏起来，而是把故障写在退单小票上：哪台机器、什么原因、建议怎么办。前台才能转头对顾客说人话。

它只接住“做坏了”的 Exception，不接住“关店 / 停电”级别的 BaseException——所以 Ctrl-C 仍然能停。

完整可运行代码：boba/tool_protocol.py。五个测试覆盖缺参数、未知工具、工具异常、成功和“每个调用恰好一个结果”。在仓库根目录跑：

python3 -m unittest discover -s tests -v

5. 四种小票，四句人话

错误码不是给程序员看的日志，是给前台（模型）看的下一步提示。同一张退单小票，写法不同，前台的反应就不同。

小票上写 前台对顾客说 前台不能做
missing_argument
“order_create 缺少 size, ice, sugar”		 “您要中杯还是大杯？冰量、糖度呢？” 自己猜“中杯少冰三分糖”
unknown_tool
“没有注册工具：get_discount”		 “目前没有会员折扣，要不要看看今天的第二杯半价？” 原样再喊一次“get_discount”
tool_failed
“inventory_check 失败：冰箱传感器离线”		 “稍等，我确认一下库存。” 假装库存正常，直接下单
ok: true
“B1001 中杯少冰三分糖 12 元”		 “中杯少冰三分糖，12 元，大约 6 分钟。” 再多问一遍已经答过的规格

退单小票的三段式：code 是暗号，message 是事实，hint 是下一步。只写“出错了”，前台只能干瞪眼。

后面还会遇到两种退单：permission_denied（店规不让做，比如“未成年人不能买酒”）和 budget_exhausted（打烊时间到了）。处理原则一样：写清楚原因和下一步，不让前台猜。

6. 窗口不守规矩，店里会怎样

协议不是为了好看。每一条规矩，都对应一个会真实发生的差评。

窗口偷的懒 店里发生什么 顾客看到什么
单子没写冰量，师傅自己猜 顾客要热饮，拿到冰的 “我不是说了热的吗？”
菜单没有的菜，硬做 做不出来，或者用了不该用的料 等半天，最后退单
封口机卡住，假装做好了 漏杯、洒袋 拿到一杯漏的
小票单号写错 出杯给错人 等不到，或被别人拿走
把异常直接扔出窗口 前台被烫，循环崩掉 没人理，对话结束

窗口口诀：接单看单号，做前查菜单，缺项问顾客，坏了写退单，小票回前台。

8. 这一课没修的设备

  • 没装完整配方校验：只查了必填和未知参数，还没查类型、枚举、范围。
  • 没装自动重做：tool_failed 先交回前台，不自动重试。
  • 没装故障统计：哪种退单最多，还没统计。
  • 没装监控录像：trace 还没落盘，出事只能靠回忆。
  • 没装店规否决：permission_denied 只占了个位置。
