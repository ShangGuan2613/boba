Boba · Lesson 04

店规：有些单，后厨不能接

预算管“做多少”，护栏管“能不能做”。模型再会说话，也不能绕过店规。

约 14 分钟 · 前置 Lesson 03 · 护栏速查 · Harness 地图

1. 最危险的失败，是“成功执行了不该做的事”

一位顾客走进店里：“来 20 杯珍珠奶茶，公司团建。”

前台（模型）没有店规概念。它看到需求，生成调用：

model.turn      tool_use  order_create(quantity=20)
tool.result     ok        B1001，20 杯，240 元
run.end         ok

没有报错，没有异常，循环正常结束。但这 20 杯把今天剩下的珍珠全用完了，后面的顾客一杯也买不到。

工具协议防的是“做失败”，护栏防的是“做成功但不该做”。模型不会自己想起店规；你不拦，它就照做。

2. 店规贴在窗口上

店规不是收银台旁边的小字，也不是提示词里的一句“请不要超过 10 杯”。它是窗口在接单前必须执行的检查：

护栏是代码级否决：在工具执行之前检查；拒绝时回一张 permission_denied 小票，工具一次都不执行。

预算（Lesson 03） 护栏（本课）
管什么 做多少：轮数、次数、时间 能不能做：数量、年龄、权限、库存红线
检查点 模型 / 工具动作之前 工具执行之前
拒绝后 收尾，给 fallback message 模型解释规则，循环可以继续
状态 / 错误码 max_turns、max_tool_calls、timeout permission_denied、invalid_quantity
自己坏了 硬停 默认拒绝（fail closed）

3. 四种单子，窗口接不接

点标签，看同一套店规在不同单子前怎么反应。注意最后一单：它暴露了本课护栏的一个洞。

5 杯：正常接单

调用
{"tool_use_id": "call_1", "name": "order_create",
 "args": {"item": "boba_milk_tea", "quantity": 5, ...}}

回填
{"tool_use_id": "call_1", "is_error": false,
 "content": {"ok": true, "data": {"order_id": "B1001",
   "quantity": 5, "total": 60}}}

后厨：动手做了 5 杯。护栏放行。

11 杯：超过单笔上限

调用
{"tool_use_id": "call_2", "name": "order_create",
 "args": {"item": "boba_milk_tea", "quantity": 11, ...}}

回填
{"tool_use_id": "call_2", "is_error": true,
 "content": {"ok": false, "error": {
   "code": "permission_denied",
   "message": "单笔最多 10 杯，这次是 11 杯。",
   "hint": "不要自动拆单绕过；先向顾客解释店规，必要时转人工。"}}}

后厨：一次都没动手。前台转头对顾客解释店规。

20 杯拆两单：每单 10 杯

call_1  order_create(quantity=10)  →  ok，B1001
call_2  order_create(quantity=10)  →  ok，B1002

合计：20 杯。两条护栏各自都通过。

后厨：做了 20 杯。这就是本课护栏的洞：它只看单笔，不看这次会话一共做了多少。下一课用 session 级规则补。

4. 代码：先过店规，再让工具动手

一条护栏只回答一个“能 / 不能”。单笔上限大概长这样：

class MaxCupsPerOrder:
    name = "max_cups_per_order"

    def __init__(self, limit=10):
        self.limit = limit

    def check(self, call):
        if call.name != "order_create":
            return ALLOW

        quantity = call.args.get("quantity", 1)
        if quantity > self.limit:
            return GuardrailDecision(
                False,
                "permission_denied",
                f"单笔最多 {self.limit} 杯，这次是 {quantity} 杯。",
                "不要自动拆单绕过；先向顾客解释店规，必要时转人工。",
            )
        return ALLOW

接线的地方只有一个：工具执行之前。

def run_guarded(call, tools, guardrails):
    decision = guardrails.check(call)

    if not decision.allowed:
        return denied_result(call, decision)   # 回一张退单小票

    return tools.run(call)                     # 只有放行才动手

被拒绝时，tools.run 一次都不会执行；顾客收到的是 permission_denied，不是“工具坏了”。模型可以解释、可以建议减少数量、可以转人工，但不能自己拆单绕过。

完整可运行代码：boba/guardrails.py。9 个测试覆盖放行、拒绝、非法数量、失败关闭、拒绝不执行工具等。在仓库根目录跑：

python3 -m unittest discover -s tests -v

5. 护栏的三条硬规矩

  1. 写在代码里，不写在提示词里。“请不要超过 10 杯”是建议；quantity > 10 才是店规。
  2. 检查在工具执行之前。做完再拒绝，原料已经用掉了。
  3. 拒绝也要回 tool_result。permission_denied 是模型能读懂的结果，不是异常。

失败关闭（fail closed）：护栏自己抛异常时，默认拒绝，而不是放行。店规系统坏了，不能当作“今天没有店规”。

7. 这一课没修的设备

  • 拆单绕过：单笔上限挡不住“两单各 10 杯”；需要 session 级总量规则。
  • 动态规则：年龄 / 身份证、库存红线、黑名单，还没有数据源。
  • 规则组合：现在第一条拒绝生效，还没有优先级和策略引擎。
  • 审计：护栏拒绝还没写进 trace，只能从结果反推。
  • 人工转接：hint 里说“转人工”，但还没有真正的交接通道。
