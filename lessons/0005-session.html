Boba · Lesson 05

小票与订单夹：同一桌的单，不能各算各的

单笔护栏只看手里这张单；订单夹记得这一桌从坐下到现在一共点了多少。

约 15 分钟 · 前置 Lesson 04 · 状态速查 · Harness 地图

1. 上一课留下的洞：两单各 10 杯

顾客要 20 杯。前台没有一次下 20 杯，而是拆成两张单：

call_1  order_create(quantity=10)  →  ok，B1001
call_2  order_create(quantity=10)  →  ok，B1002

两条单笔护栏各自都通过。合计：20 杯。

后厨做了 20 杯，珍珠用完了。护栏没有坏，它只是只看自己收到的这一张单：第一张 10 杯，没超；第二张也是 10 杯，也没超。

店里的老员工不会这么看。她会翻开这一桌的订单夹：已经有 10 杯了，再加 10 杯就是 20 杯，不能接。

单笔护栏看“这一张单”；session 级护栏看“这一桌到目前为止”。要补这个洞，先得让店里有一本跨轮次、跨单子的订单夹。

2. 订单夹是什么：桌号 + 已下的单

订单夹不是模型脑子里的记忆。模型这一轮能看见的是 messages；订单夹是柜台后面真实存在的一本夹子，由 Harness 持有。

messages（上下文） session state（订单夹）
谁持有 这一轮发给模型的消息 Harness / 店铺系统
里面有什么 用户说了什么、模型说过什么、工具返回了什么 桌号、已下的单、每单数量、状态
会忘吗 会被截断、摘要、遗漏 只要没删，就一直在
模型能改吗 能“说”自己记得什么 不能直接改；只能通过工具成功后的提交
出了分歧信谁 参考 以订单夹为准

这本夹子最少要有三样东西：

  • 桌号（session_id）：这是哪一桌的夹子。
  • 订单列表：这一桌已经成功下了哪些单。
  • 合计：从订单列表算出来的总杯数，护栏直接读它。

关键：模型看不见订单夹，除非工具把结果返回给它。所以“刚才点了 5 杯”只是模型的一句话；订单夹里写着 10 杯，就以 10 杯为准。

3. 四种时刻，订单夹怎么反应

点标签，看同一本订单夹在四个场景里的状态。注意第二单和第三单：一个修好了拆单，一个暴露了串桌的风险。

3 号桌先点 5 杯：正常记账

session = table-3
订单夹: []

call_1  order_create(quantity=5)
  护栏: 0 + 5 = 5 ≤ 10  →  放行
  后厨: 做 5 杯
  记账: 订单夹 → [B1001 × 5]

订单夹合计: 5 杯

要点：先检查，再执行，成功后记账。三步顺序不能换。

3 号桌要 20 杯，拆成两单：第二单被挡

session = table-3
订单夹: []

call_1  order_create(quantity=10)
  护栏: 0 + 10 = 10 ≤ 10  →  放行
  记账: 订单夹 → [B1001 × 10]

call_2  order_create(quantity=10)
  护栏: 10 + 10 = 20 > 10  →  permission_denied
  后厨: 一次都没动手
  记账: 不写；订单夹仍是 [B1001 × 10]

订单夹合计: 10 杯

要点：第二单被拒，不是因为单笔超限，而是因为“订单夹已有 + 本次”超了。拆单不再能绕过。

5 号桌来查 3 号桌的订单号：查无此单

session = table-5
订单夹: []

call_3  order_status(order_id="B1001")
  工具只查 table-5 的订单夹
  B1001 不在这里
  →  not_found

不能返回“B1001 是 10 杯珍珠奶茶，属于 3 号桌”。
那等于把邻桌的订单详情泄露了。

要点：每个 session 只能看自己的订单。跨桌查询不只要拒绝内容，连“这个订单号存不存在”都不该确认。

模型在第二轮说“刚才只点了 5 杯”：信订单夹

messages 里模型说:
  “您刚才点了 5 杯，还可以再加 5 杯。”

订单夹里:
  [B1001 × 10]

call_4  order_create(quantity=5)
  护栏读订单夹: 10 + 5 = 15 > 10
  →  permission_denied

模型的说法可以错、可以过期；
订单夹是权威状态。

要点：不要让模型“自己记住总量”。它负责说话，订单夹负责记账；护栏只信订单夹。

4. 代码：一本订单夹，一条总量护栏

订单夹只需要记住“这一桌”的单。合计不单独存，直接从订单列表算，避免两个数对不上：

@dataclass
class SessionState:
    id: str
    orders: list[dict] = field(default_factory=list)

    @property
    def total_cups(self):
        return sum(order["quantity"] for order in self.orders)

    def add_order(self, order_id, quantity):
        self.orders.append({
            "order_id": order_id,
            "quantity": quantity,
            "status": "draft",
        })

桌号到订单夹的映射由 SessionStore 管。没见过的桌号先开一本空夹子；同一个桌号每次拿到的是同一本。

class SessionStore:
    def __init__(self):
        self._sessions = {}

    def get(self, session_id):
        if session_id not in self._sessions:
            self._sessions[session_id] = SessionState(session_id)
        return self._sessions[session_id]

护栏不再只读 call.args，还要读 session.total_cups：

class MaxCupsPerSession:
    name = "max_cups_per_session"

    def __init__(self, limit=10):
        self.limit = limit

    def check(self, call, session=None):
        if call.name != "order_create":
            return ALLOW

        if session is None:
            return GuardrailDecision(
                False, "guardrail_error",
                "缺少 session，无法检查会话总量。",
                "默认拒绝；检查护栏接线。",
            )

        quantity = call.args.get("quantity", 1)
        if session.total_cups + quantity > self.limit:
            return GuardrailDecision(
                False, "permission_denied",
                f"本次会话最多 {self.limit} 杯，"
                f"已有 {session.total_cups} 杯，再加 {quantity} 杯会超。",
                "不要拆单；向顾客解释店规，必要时转人工。",
            )
        return ALLOW

接线还是同一个入口，只是多传一个 session。真正把“检查”和“记账”分开的是 place_order：

def place_order(session, call, tools, guardrails):
    result = run_guarded(call, tools, guardrails, session)

    if not result.is_error:
        data = result.content["data"]
        session.add_order(data["order_id"], data["quantity"])

    return result

为什么“记账”必须在成功之后？被拒绝的单如果也写进订单夹，就会产生“幽灵订单”：后厨根本没做，但合计已经占用了额度，下一张正常单反而被拒。状态要记录事实，不记录意图。

python3 -m unittest discover -s tests -v

5. 状态的四条硬规矩

  1. 状态由 Harness 持有，不由模型持有。模型可以说“我记得”，但护栏只读订单夹。
  2. 先读状态检查，再执行，成功后写状态。顺序反了，就会出现超量、幽灵订单或漏记。
  3. session 之间必须隔离。桌 5 只能看桌 5 的单；跨桌查询返回查无此单。
  4. 状态要能被工具读回来。模型不需要直接看订单夹，但需要一个只读工具把“本桌合计 / 订单状态”作为 tool_result 返回。

一句话：护栏读状态，工具改状态，模型只看结果。把这句话记住，后面做多轮、多用户、持久化时都不会乱。

7. 这一课没修的设备

  • 持久化：订单夹现在只在内存里，进程一重启就没了；真实店铺要落库。
  • 并发：两桌同时下单时，“读合计 → 检查 → 写入”可能撞车；需要事务、锁或原子更新。
  • 订单号：示例里的 order_create 永远返回 B1001；真实系统要生成唯一订单号。
  • 状态增长：订单夹会越来越长；需要归档、摘要和只读查询，不能整本塞回模型上下文。
  • 权限分级：现在只按桌号隔离；店员查单、店长看报表是另一种授权模型。
  • 审计：状态变化还没写进 trace，出了纠纷无法还原“谁在什么时候改了什么”。

下一课：监控与复盘——trace / eval。把每一张单、每一次拒绝、每一次状态变化都记下来。
