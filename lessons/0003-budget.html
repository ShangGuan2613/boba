Boba · Lesson 03

打烊铃：给循环一个尽头

模型只负责下一杯；它不会看表，也不会数自己调了多少次工具。店长必须在墙上装三个闸门。

约 14 分钟 · 前置 Lesson 02 · 预算速查 · Harness 地图

1. 一家永远不打烊的店

晚上十点，最后一单。库存传感器坏了，后厨窗口回了一张退单小票：tool_failed。前台（模型）看到失败，决定再试一次；窗口又回 tool_failed；再试……

call_1   inventory_check  →  tool_failed
call_2   inventory_check  →  tool_failed
call_3   inventory_check  →  tool_failed
...
call_41  inventory_check  →  tool_failed

模型没有“我该停了”的概念。它只会根据上下文生成下一步；你不喊停，它就继续。顾客等到打烊，店长（Harness）还在后厨门口陪着排队。

问题不在模型笨，而在店里没有铃。

2. 墙上三个闸门

店长要在墙上装三个硬闸门。它们不是提示词里的“请尽快”，是循环里的代码检查：

闸门 店里的话 默认值 铃响后的状态
max_turns 最多接待几轮 8 轮 max_turns
max_tool_calls 最多做几次工具 16 次 max_tool_calls
max_seconds 最多让顾客等多久 60 秒 timeout

预算是店规，不是建议。模型不能自己决定加班；闸门装在 Harness 里，到点就落闸。

还有一条同样重要：检查要放在花钱之前。先看额度，再决定要不要做。做完才检查，预算就变成了“事后道歉”。

3. 打烊铃模拟器

每点一次“调用工具”＝模型决定做一轮并调用一次工具；也可以让顾客继续等。看额度怎么被扣完，铃响后顾客收到什么。

工具调用0 / 3
对话轮数0 / 5
等待时间0 / 30 秒

店刚开门，预算充足。

注意两件事：第一，额度用完后的那一次调用，工具没有执行；第二，铃响后顾客仍收到一张说明小票，不是空白。

4. 代码：闸门放在花钱之前

先看预算本身。它只管三件事：数轮数、数工具、看表。

@dataclass
class Budget:
    max_turns: int = 8
    max_tool_calls: int = 16
    max_seconds: float = 60.0
    turns: int = 0
    tool_calls: int = 0

    def _check_timeout(self):
        if self.elapsed >= self.max_seconds:
            raise BudgetExceeded("timeout", ...)

    def start_turn(self):
        self._check_timeout()
        if self.turns >= self.max_turns:
            raise BudgetExceeded("max_turns", ...)
        self.turns += 1        # 再扣一轮

    def start_tool(self):
        self._check_timeout()
        if self.tool_calls >= self.max_tool_calls:
            raise BudgetExceeded("max_tool_calls", ...)
        self.tool_calls += 1   # 再扣一次

每个闸门只拦自己的动作：轮数闸门只管模型调用，工具闸门只管工具执行；超时两个都管。这样最后一轮仍然可以调用工具，工具额度用完后也还能留一个收尾回合——只要模型不再要工具。

把它放进第 1 课的循环里，闸门就在两个地方落下：

try:
    while True:
        budget.start_turn()              # 进门先看表
        turn = model(messages)

        if turn.type == "text":
            return RunResult(status="ok", message=turn.text)

        for call in turn.tool_calls:
            budget.start_tool()          # 动手前再看一次
            result = registry.run(call)
            messages.append(result)

except BudgetExceeded as stop:
    if pending_call:
        messages.append(budget_error(pending_call.id, stop.status))
    return RunResult(status=stop.status, message=stop.user_message)

为什么不能直接 break？

打烊时，如果后厨窗口手里还攥着一张单子，不能直接关灯走人。你要在单子上盖一个“未完成”的章，放回前台；否则下一班的人看到一张没有结局的单子，不知道是该做、该退，还是该问顾客。

代码里也一样。假设模型刚发出 tool_use call_17，预算就响了。如果你直接 break：

messages = [
    user("库存还有吗？"),
    assistant(tool_use call_17),   # 单子递进来了
    # break：没有 tool_result
]

这条对话就留下了一个“悬空的 tool_use”。下一次模型调用（或恢复会话）会看到一个没有结果的工具请求：真实 Messages API 可能直接报协议错误；就算不报错，模型也只能重复调用或凭空猜。顾客那边则是一片空白。

正确做法是先补小票，再收工：

messages.append(budget_error_result(call_17, stop.status))
return RunResult(status=stop.status, message=stop.user_message)

打烊不是把单子撕了，是给单子盖章。break 只停住了 Harness，没有关掉那张单子；补上 tool_result，才是把单子交回前台。

完整可运行代码：boba/budget.py。八个测试覆盖轮数上限、工具上限、超时、优先级、用量快照，以及铃响时给待执行调用补结果。在仓库根目录跑：

python3 -m unittest discover -s tests -v

5. 铃响之后，顾客不能看到空白

闸门是给 Harness 看的，不是给顾客看的。顾客只该听到一句人话：

状态 店里的话 顾客看到
max_turns 今天聊得够久了 “今天先聊到这里，您要的我都记下了，稍后人工同事跟进。”
max_tool_calls 后厨做不过来了 “今天先做到这里，您这杯已经排上，稍后确认。”
timeout 排队太久了 “现在排队比较久，我先帮您留单，稍后再试。”
ok 正常出杯 “中杯少冰三分糖，12 元，大约 6 分钟。”

状态给日志，message 给顾客。不要把 max_tool_calls、timeout 这种内部暗号直接甩给顾客，也不要用“系统繁忙”糊弄过去。

6. trace 里也要有铃声

铃响以后，店长要能回答：是轮数、工具数，还是时间？当时已经做了多少？没有 trace，只剩一句“好像卡住了”。

run.start        budget={"max_turns": 8, "max_tool_calls": 16, "max_seconds": 60}
model.turn 1     tool_use inventory_check
tool.result      call_1  tool_failed
...
budget.exhausted status=max_tool_calls
                 used={"turns": 3, "tool_calls": 16, "elapsed": 12.4}
tool.result      call_17 budget_exhausted
run.end          status=max_tool_calls

trace 让“打烊”变成一个可复盘的事件，而不是一次神秘消失。

8. 这一课没修的设备

  • 工具挂死：现在只在调用前后看表；工具自己卡住，不会被打断。真中断需要线程 / 子进程超时。
  • 单工具预算：没有限制某个工具最多查几次，比如库存查询不能刷 100 次。
  • token 预算：没有限制上下文长度，长对话仍可能撑爆窗口。
  • 重试与退避：没有自动重试，失败先交回前台。
  • 限流：没有按顾客或门店限流。

下一课：店规——护栏。预算管“做多少”，护栏管“能不能做”。
