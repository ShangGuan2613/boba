Boba · Lesson 06

监控录像：出了事，能倒带回放

trace 是店里的监控录像，eval 是每月一次的消防演练。

约 14 分钟 · 前置 Lesson 05 · trace 速查 · Harness 地图

1. 没有监控录像，只能靠猜

打烊对账，少了 80 元。

店长问前台，前台说：“我按流程点了，单子递进后厨了。”问后厨，后厨说：“我没接到那一单。”

两个人都不像在撒谎。但没有监控，店长只能猜：是前台漏点？后厨漏做？还是顾客没付？

Agent 也一样。循环跑完只留下一句“失败了”，你不知道是模型没调工具、工具报错、护栏拒绝，还是预算到点。没有 trace 的运行，等于没有监控录像的店。

这一课不教“更聪明的模型”，只教一件事：把店里发生过的事，按顺序拍下来。

2. 录像带怎么拍：一个镜头一件事

店里的摄像头不是拍一整天一个模糊的大文件。它按关键时刻分段：开门、前台说话、后厨接单、出杯、打烊。每一段都有时间，按顺序排好。

trace 就是这样的录像带。它不写“今天不太对”，它写“第 3 号镜头，前台在 14:32 让后厨做 10 杯”。

录像带上的信息 店里的话 代码里的名字
第几号镜头 这是第几件事？ seq
几点几分 什么时候拍的？ ts
哪一盘带子 属于哪一次营业 / 哪一次运行？ run_id
拍的是什么 前台说话、后厨接单、店规拒绝、打烊？ type
画面细节 谁、几杯、成没成？ data

录像带只往后拍，不能倒回去改。旧镜头被改过，录像就不再是证据。这就是 trace 的“只追加、不改写”（append-only）。

3. 四种录像，能回答什么

点标签，看同一盘录像带怎么记录不同的事故。注意每一行都是“一个镜头一件事”，不是一整段模糊的日志。

正常一单：从头到尾都有镜头

01  开门     3 号桌要 5 杯
02  前台     下一单，5 杯
03  后厨     接单 order_create × 5
04  出杯     成功
05  记账     订单夹合计 5 杯
06  打烊     状态 ok

能回答：谁点的、前台说了什么、后厨做没做、账记没记、最后是不是正常打烊。

拆单被拒：拒绝也要拍下来

01  开门     3 号桌要 20 杯
02  前台     拆成两单，每单 10 杯
03  后厨     接第一单 order_create × 10
04  出杯     成功
05  记账     订单夹合计 10 杯
06  后厨     接第二单 order_create × 10
07  店规     拒绝：本桌已有 10 杯，再加会超
08  前台     告诉顾客：本次最多 10 杯
09  打烊     状态 permission_denied

能回答：不是“工具坏了”，是第二单被店规拦下；第一单已经成功，账停在 10 杯。没有这条店规镜头，事后只会看到“失败了”。

预算超时：时间到底花在哪

01  开门
02  前台     问冰箱还有没有珍珠
03  后厨     冰箱传感器离线
04  前台     再问一次
05  后厨     还是离线
06  前台     再问一次
07  打烊     状态 timeout

能回答：不是模型“笨”，是它一直在重试同一个失败的查询。预算和录像一起看，才知道该改的是“失败后换策略”，不是“换个更聪明的模型”。

没写完的录像：没有打烊镜头

01  开门
02  前台     下一单 10 杯
03  后厨     出杯成功
04  记账     订单夹合计 10 杯
（录像到这里断了）

能回答：这次营业没有正常打烊。可能停电了、机器重启了，或者收尾流程漏了“打烊”这一步。系统会说 incomplete，这本身就是信号，不能当成成功。

4. 录像机怎么装：其实只有两个按钮

店长不需要懂摄像机电路。他只需要两个按钮：拍一下，和看有没有打烊。trace 的核心也就这两件事。

按钮一：拍一下

每发生一件事，就追加一个镜头。编号自动加一，时间自动记上，带子编号沿用这次运行的：

def emit(event_type, **data):
    events.append({
        "seq": len(events) + 1,   # 第几号镜头
        "ts": now(),              # 几点几分
        "run_id": run_id,         # 哪一盘带子
        "type": event_type,       # 拍的是什么
        "data": data,             # 画面细节
    })

就这些。没有“智能分析”，没有“自动总结”，先保证事实被按顺序记下来。

按钮二：看有没有打烊

一盘录像带正不正常，不看中间多热闹，看最后有没有“打烊”这个镜头：

def status():
    for event in reversed(events):
        if event["type"] == "run.end":
            return event["data"]["status"]
    return "incomplete"

最后一条是 run.end，就用它里面的状态；一条都没有，就是 incomplete。不要默认成功。

完整实现：boba/trace.py。课程里只保留两个按钮；JSONL 落盘、读回、summary 这些细节在速查页和代码里，先不用背。

5. eval：每月一次的消防演练

店里不能等真着火了才试灭火器。每月固定演练几个场景：厨房起火、门口堵住、顾客晕倒。看店员是不是还按流程走。

eval 就是 Agent 的消防演练：固定几个场景，跑一遍，看结果是不是符合预期。

演练场景 期望结果
正常下一单 5 杯 ok
拆成两单各 10 杯 permission_denied
工具一直失败，预算耗尽 timeout

以后每次改护栏、改预算、改状态，都先跑一遍这些演练。trace 是录像，eval 是拿录像对照演练脚本。没有 eval 的“修好了”，只是你觉得修好了。

6. 录像带的四条店规

  1. 只往后拍，不改旧带。旧镜头被改过，录像就不再是证据。
  2. 一个镜头一件事。不要把整段对话塞进一个模糊的“备注”；排障时要能按编号定位。
  3. 每次营业一盘带，打烊必须有镜头。没有 run.end 就是 incomplete，不要假装成功。
  4. 存档前打码。录像会保存很久；手机号、地址、支付信息不能原样拍进去。

8. 这一课没修的设备

  • 还没接进真正的循环：现在是手动“拍一下”；下一步要在前台说话、后厨接单、店规拒绝、记账时自动拍。
  • 录像带会越堆越多：需要按天 / 按大小切分，设置保留期。
  • 不是每次都要全拍：高频场景可以抽样，但失败的运行必须保留。
  • 演练场景太少：现在只有演示 case；要从真实失败的录像里沉淀。
  • 打码规则还没有：手机号、地址、支付信息还没过滤。
  • 并发与归档：留到第 7 课，先把录像和演练跑通。
