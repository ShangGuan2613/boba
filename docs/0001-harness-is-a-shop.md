# 0001 · Harness 就是一家门店

- 状态：已采纳
- 日期：2026-11-19
- 决策者：项目初始版本

## 背景

Agent 框架的术语很容易飘：runtime、orchestrator、tool layer、memory、guardrails……每个词都正确，但放在一起就失去实感。第一个 MVP 需要一套**能直接做取舍**的参照物，而不是又一层抽象。

我们选择奶茶店作为核心喻体和第一个应用场景：

- 每个人都理解一家奶茶店如何运转；
- 角色、边界、状态、失败模式都很具体；
- 小团队能在一天内把最小闭环跑通；
- 它天然包含“多轮对话 + 真实状态变更 + 人工规则 + 流水记录”。

## 决定

把 **Harness 定义为门店运营体系**，把 Agent 定义为店员，把 Model 定义为茶底/原料，把 Tool 定义为设备/工位，把 Guardrail 定义为店长守则，把 Trace 定义为小票流水。

框架层只保留：

```
Agent(system_prompt, tools)
Harness(agent, model, resources, guardrails, config)
Tool(name, description, input_schema, handler)
Model.generate(system, messages, tools) -> ModelTurn
```

奶茶店（`boba/shop/`）是第一个租户，不是框架本身。Harness 里不出现“菜单”“库存”“订单”这些词。

## 为什么不是反过来

**先写通用平台，再找场景**，通常得到两种东西：过度抽象的空壳，或者把第一个场景硬编码进内核的假平台。

**先把一家店开起来**，会逼出真实问题：工具失败了模型怎么继续？预算耗尽时历史怎么保持合法？护栏该拦在哪一层？小票该记什么？这些问题有具体答案，而答案可以迁移到下一个场景。

## 映射与后果

| 喻体 | 代码 | 设计后果 |
| --- | --- | --- |
| 店员 | `Agent` | 行为由配方卡（prompt）和技能（tools）决定，不持有全局状态 |
| 门店运营 | `Harness` | 唯一知道循环、预算、派发、会话历史的地方 |
| 设备 | `Tool` | 普通函数 + JSON Schema；预期失败用 `ToolError` 表达 |
| 茶底 | `Model` | 可替换协议；离线脚本模型让 CI 不依赖网络 |
| 库存 | `resources` | 应用状态由应用注入，Harness 不解释 |
| 店长守则 | `Guardrail` | 工具执行前的否决权；异常时 fail closed |
| 小票 | `Trace` | 每个事件可回放；未来的评测数据底座 |
| 一次接待 | `Session` | 多轮上下文复用；不等于持久化 |

几个由此固定的规则：

1. **工具调用必须配对结果。** 包括被护栏拒绝、未知工具、预算耗尽——否则会话历史损坏。
2. **预算必须有限。** 门店不能无限接待同一个顾客；`max_turns` / `max_tool_calls` / `max_seconds` 是硬边界。
3. **护栏不靠模型自觉。** 提示词是配方卡，护栏是店长；后者在代码里。
4. **小票不裁剪成“摘要”。** 原始事件先完整落下，展示层再做裁剪。
5. **应用状态不塞进 Harness。** 库存、订单属于 `shop`，Harness 只通过 `ToolContext.resources` 传递。

## 非目标（MVP）

- 不做通用工作流引擎；
- 不做多 Agent 编排；
- 不做持久化、鉴权、多租户；
- 不做 Web UI；
- 不承诺与任何特定模型厂商绑定。

## 被否决的方案

- **纯文档先行**：概念会失去约束，代码容易变成示例拼盘。
- **直接接真实模型做 demo**：无法离线复现，测试和 CI 不可控；先用确定性脚本模型跑通链路。
- **把所有能力塞进一个大 `Agent` 类**：Harness/Agent/Model/Tool 的边界会消失，后续无法替换任何一层。

## 后续

下一步不是加更多抽象，而是把这家店开得更真：持久化、并行工具、流式输出、评测（试饮会）、多角色（前厅/后厨/店长）。见 [ROADMAP](../ROADMAP.md)。
