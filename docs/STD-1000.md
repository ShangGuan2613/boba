# STD-1000 · 经验沉淀标准（v0.1 工作草案）

> **状态**：草案，等待学习者批准。
> 学习者表示也没有现成的 STD-1000 定义。为了让“所有 agent 必须沉淀”可执行，先定义这个最小标准；批准后升为 v1.0。
> 编号“1000”由学习者指定；本文件不解释编号含义。

## 目的

把一次具体的失败或决策，蒸馏成**下一次可直接复用**的经验，避免下一个 agent 重新踩坑。

## 什么时候必须写

- 修了一个非显而易见的 bug。
- 做了一个会影响后续设计的决策。
- 学习者的 review 修正了课程或实现。
- 一次任务失败，且失败原因值得复用。
- 引入或删除一个 Harness 部件。

## 一条记录只写一件事

不要写“本次任务总结”。任务总结用 STAR；STD-1000 只写从中提炼出的那一条经验。

## 字段

```md
### STD-YYYYMMDD-NNN · {一句话标题}

- **情境**：在什么场景下发生
- **问题**：可观察到的失败或冲突
- **决策**：改了什么（具体到代码/规则/流程）
- **证据**：文件、测试、trace、学习者反馈的链接
- **可复用规则**：下次遇到类似情况，应该怎么做（祈使句，可检验）
- **失效边界**：什么条件下这条规则不再成立
- **关联**：课程 / 代码 / STAR 记录
- **状态**：proposed | confirmed | superseded
```

## 质量门槛

- **没有证据，不写**。证据可以是测试、trace、diff、学习者原话。
- **一条记录只回答一个问题**。标题里出现“和”“以及”时，拆成两条。
- **规则必须可检验**。“注意代码质量”不合格；“工具报错也必须回填 `tool_result`”合格。
- **写失效边界**。没有边界的经验，通常只是口号。
- **不重复 STAR**。STAR 记录发生了什么；STD-1000 记录以后怎么做。

## 与 STAR 的关系

| 格式 | 回答的问题 | 存放 |
| --- | --- | --- |
| STAR | 这次任务发生了什么？ | Notion 的 STAR 日志 |
| STD-1000 | 以后遇到类似情况怎么做？ | Notion 的 STD-1000 经验 + 本文件索引 |

## 示例

```md
### STD-20261119-001 · 不要把模型等同于执行者

- **情境**：第 1 课用“店员”比喻 Model。
- **问题**：学习者指出模型只思考、不执行；店员本身才是执行方，比喻把执行责任错放给了模型。
- **决策**：改为“店员（整个人）= Model + Harness；Model 是判断与话术，Harness 是手脚、设备与店规”。
- **证据**：`learning-records/0001-model-is-not-the-barista.md`；第 1 课 review。
- **可复用规则**：讲 Agent 时，先把“判断”和“执行”拆开，再给角色比喻。
- **失效边界**：当讨论的是纯文本生成、不涉及工具执行时，可以只谈模型。
- **关联**：Lesson 01；STAR 2026-11-19。
- **状态**：proposed
```
